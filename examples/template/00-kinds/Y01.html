Y01 The kinds of content

This sheet is the catalogue, and every block in it is an example of itself. To find out what a kind is, look at the block that carries that kind — it is written the way the kind asks for.

1 Why label the kind

Because "is this any good?" is not the same question for a heading and for a diagram.

With no kind, every quality rule turns into spoken convention — and spoken convention dies on the third person who joins the project. With a kind, the rule belongs to the kind, not to somebody's memory.

Information callout. Every callout says which sort it is — info, warning, ok or forbidden. Without that it is just a paragraph with a border, and the colour means nothing.

What a kind changes, and what it does not:

  • It changes what is demanded before approval — an image needs a description, a decision needs an owner.
  • It does not change who approves, nor how the fingerprint is computed. There is still one lock.

2 The kinds that ask something of you

Most ask for nothing. These ask, and the engine collects.

KindWhat it demandsWhy
imagean alt what is inside the image never enters the fingerprint; the description is the only reviewable part
diagramto be text, not a picture a PNG has no useful fingerprint: recompressing changes the bytes without changing the meaning
tablea header row with no <th>, nobody on a screen reader knows what each cell is
decisionan owner and a deadline an open question with no owner is not open — it is lost
colorsthe value of the colour "primary blue" is not a value; #2E6E5B is
listtwo items a one-item list is a paragraph in a bad costume
rulethe test that defends it a rule nobody proved is a rule nobody can check — and nothing tells you when it stops being true

A diagram is text, and so it falls under the lock like any paragraph:

flowchart LR
  E[the text changed] --> D{did the fingerprint change}
  D -->|yes| A[turns yellow]
  D -->|no, but what it rests on changed| V[turns red]

The palette, with the value alongside: #2E6E5B for the brand, #C94A4A for what needs attention, #16212E for the ink.

Domain rule. A block code appears once per page. Two blocks sharing data-code are not two blocks to the engine — the second one silently replaces the first, and an approval given to one text ends up filed against another.

This block carries data-proof, and that is the whole difference between a rule and a strong opinion: it names the test that defends it. A rule is not a contract — nobody outside promised anything — and not a model: it holds whatever shape the data is stored in.

3 Dependency, and what it unlocks

Declaring what a block rests on is what wires up the red light.

This block declares data-depends="Y01.1.1". If that one changes, this one turns 🔴 — not because it became wrong, but because it became suspect, and somebody has to check whether it is still true.

Open decision, with owner and deadline. How much of the dependency can the tool propose on its own, instead of waiting for somebody to declare it? Two blocks that talk about the same term probably depend on each other — but "probably" is not enough to hold back an approval.
